## How "same assertion" was checked

Each old/new pair is compared after replacing only the timing label with `<T>`:
new labels `[lo, hi] s: <why>` (and `[lo, hi] sends: <why>`), old labels `[0-3s]`, `[4-7.5s (...)]`,
`<4 s`, `1 s`, `200 ms (...)`, `5-6s (...)`, `5-8 (...)`. Everything before the label (exit code,
board state, notification text and key, counts) must match byte for byte; all 42 pairs do.
Nothing was dropped and no line was added without a removed counterpart (42 removed, 42 added).

The edges are unchanged or set from code constants: every old bucket's range is contained in, or
equal to, the new bound (e.g. `<4 s` became `[0, 4] s`; the lost-board bucket `4-7.5s` became
`[4, 8] s`, the 1 s periods `[0.85, 1.25)` became `[0.75, 1.5]`).

### `ota_service: exit 0 within <4 s` (shutdown.txt, SIGINT section)

Replaced by `ota_service: exit 0 within [0, 4] s: slowest loop: kElodinRecvTimeoutMs 3000, + 1 s`.
The exit code is still asserted exactly (`exit 0`; a different code, or `None` for a process still
alive after the 30 s deadline, changes the line). The bound is the same 4 s as before; its label
cites the slowest loop of the services in that SIGINT batch (heartbeat_service's 3000 ms Elodin
receive timeout), since all six share one bound. ota_service's own SIGTERM line in the same golden
carries its tighter bound, `[0, 1.6] s: select timeout 1 s, + 0.6 s`.
